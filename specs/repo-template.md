# Repo template

The repo template, in `templates/default-repo/`, gives every repository RepoCop onboards the same rules, skills and spec layout, so the developer's agent works the same way in each, and RepoCop can read what it needs from each. Its files reach a repository only through a [template sync](template-sync.md), which compares them with the repository's default branch and commits the ones the developer picks on a branch of its own. How to edit it is in `templates/README.md`.

## How it reaches a repository

- **Copied, never linked.** A repository never depends on RepoCop's template folder at runtime and never links to it. Changing a template file therefore reaches a repository only when someone syncs and merges, and a repository whose default branch is behind shows so on RepoCop's pages.
- **Each file has a kind** ([template-sync.md › File kinds](template-sync.md#file-kinds)), which decides what a sync offers once the repository has it. A managed file follows the template, and a sync offers to overwrite it. A starter file is the repository's own once created, so a sync never offers it again: anything a repository fills in is one. A merged file is JSON a sync brings up to date with the template, adding what the template has and taking its values, and keeping what only the repository has (ADR-027).
- **Retiring a managed file reaches repositories too** (ADR-032): a sync offers to delete a marked file the template no longer ships, so dropping or renaming a managed file in the template reaches repositories. A starter or merged file holds the repository's own content, so it never carries the marker, and a sync never deletes it.
- **Not only for code** (ADR-020). An onboarded repository may produce software, writing or other media, so the shipped files don't assume code. Code-specific guidance is marked as such ("In code: …"), and verification goes through the check command the repository's own `CLAUDE.md` documents, if it has one.
- **Licensed MIT No Attribution**, in `templates/LICENSE`, beside `default-repo/` rather than in it: a license file there would be copied into every onboarded repository, where the repository's own license belongs. MIT No Attribution asks nothing of the copies, so the files a sync writes carry no obligation either.

## What every repository gets

- **Stubs to fill in.** `CLAUDE.md`, `REVIEW.md`, `specs/product.md` and `specs/architecture.md` ship as short starter stubs: section headings with one-line prompts and `_TBD_` markers, plus one example Mermaid block in `architecture.md`. Nothing requires them to be filled in; `review-requirement` flags them when they're missing or empty.
- **Rules.** The shared rules in `.claude/rules/` are managed, so they are the same in every repository. The `principles.md` rule, loaded in every session, points sessions at `specs/`, so `CLAUDE.md` doesn't need to. The managed `test-policy.md` says which tests are worth writing, the same in every repository, and `testing.md` is a starter stub where a repository fills in what that policy leaves to it, so its stack can call for more or fewer tests below the surface without forking the policy.
- **Workflows.** The skills in `.claude/skills/` are the repository's workflows, which RepoCop's requirement pages offer to run. `/implement` puts itself on the requirement's branch before it starts (`.claude/rules/specs.md` › A branch's requirement). `/open-pull-request` pushes the branch, never forced, and opens its pull request, or pushes to the one already open.
- **The guide to changes.** `specs/changes/README.md`, managed, says how a change goes from proposal to archive and how changes wait on each other, for people browsing the folder, so it reaches every repository on sync. `specs/index.md`, a starter file, only links to it; a repository created before the guide keeps its own Lifecycle section there until someone removes it.
- **The backlog graph.** `specs/changes/backlog.sh` checks each change's `depends-on` and draws the backlog in `specs/changes/backlog.md`, and runs in any repository as it is. The folder's own `.gitignore` keeps the drawing out of git, as a repository's own `.gitignore` can't be given a line by a sync. RepoCop orders requirements by the same rules ([requirements.md › Dependencies](requirements.md#dependencies)).
- **Sessions report themselves.** The settings register `.claude/hooks/session-events.sh` on the session events RepoCop shows, and again on `Stop` to hand a session the request RepoCop's page left for it: [sessions.md](sessions.md).

## Settings

`.claude/settings.json` is merged, so every repository has at least the template's entries.

- **What runs without asking.** It allows what the shipped skills run: read-only git and `gh`, `git add`, `git commit` and `git mv` (skills commit their own work), `git switch` and `git worktree list`, `make check` and `make test`, `.reviews/review.sh`, and the skills' helper scripts. `git push`, `gh pr create` and `gh pr edit` are on "ask", so pushing or changing a pull request always asks first. A repository whose check command isn't `make check` adds its own.
- **No agent attribution.** It sets `attribution` to empty strings, so commits and pull requests made in the repository carry no Claude attribution (`.claude/rules/commits.md`).
- **Fewer ways around the rules.** It turns off bypass-permissions mode, and denies Claude's file tools reading `.env` files and anything in `specs/decisions/archive/`, which the specs rule says is never loaded. A Bash command such as `cat .env` gets past those rules. Verified on Claude Code 2.1.328: the `./` form refuses Read, and Grep on the folder, and leaves the folder out of a Grep or Glob over the tree, in a session started at the checkout's top or in a worktree, even after it moves into a subfolder. A session started in a subfolder loads none of the project's settings.
- **Linux tools only on WSL.** WSL appends the Windows `PATH`, so a Linux tool that is missing can resolve to a Windows one. The SessionStart hook `.claude/hooks/linux-only-path.sh` keeps the Windows drives off the `PATH` of Claude's Bash commands and tells Claude to report a missing tool rather than use a Windows one. It does nothing off WSL. The `deny` rules block the Windows shells and anything run from `/mnt/`, including in interactive sessions where they would otherwise be approvable. Both act on the command text Claude writes, so they stop the usual forms but aren't a security boundary.
- **Pushed history stays.** `commits.md` allows amending only an unpushed commit, and an editor can push a branch without the session knowing. The PreToolUse hook `.claude/hooks/amend-only-unpushed.sh` refuses an amend of a commit already on a remote-tracking branch, and tells Claude to make a new commit. It knows only the pushes and fetches the checkout has seen. Permission rules can't do this: an auto-approved `git commit` slips past `ask`, and a hook runs whatever the permission mode.

## Branch reviews

A branch is reviewed in the repository, by the developer or the agent in their session, with an agent's own built-in review, which its vendor keeps improving. RepoCop runs none. The template gives every repository `.reviews/review.sh`, which runs Codex's review of the current branch against the default branch on `origin` as last fetched, read-only, and saves it in `.reviews/`, for `/address-review` to pick up. The folder's own `.gitignore` makes git ignore everything there but those two files. Its `/review-branch` skill runs the script in an agent's session, and the template's `/open-pull-request` then pushes the branch and opens its pull request.

- **Codex is told only what to review:** the commits since the base's merge base and, when it is given one, the requirement they deliver, which a branch not named after its requirement can't otherwise point to. That is configuration, not review logic: how to review stays Codex's. Codex takes instructions only in place of its `--base`, so they name the base as `--base` would.
- **A review changes nothing.** The script asks for Codex's read-only sandbox by name, as a host's settings can loosen it, refuses a base that isn't there, since Codex would quietly pick another, and refuses uncommitted changes, which Codex would review too. Its other refusals, and its options, are in its own header.
- **Guidance.** A repository says what a review checks and skips in `REVIEW.md`, a starter stub that any reviewer can read. Codex reads `AGENTS.md`, a starter file that only points other coding agents at `CLAUDE.md`, the rules and `REVIEW.md`. Both are the repository's own once created, so a repository that already has either keeps it. The shared `.claude/rules/reviews.md` says what every review checks: the branch's requirement as context for what the change is for, not as a list of criteria to check, with work beyond it noted rather than reported as a defect; and the tests a change adds or lacks, where the shared `.claude/rules/test-policy.md` decides which are worth having.

**Verified against the real CLI** (2026-10-12, Codex CLI 0.162.1; the facts the script and its fake rely on):

1. **Output.** The review alone is on standard output. Progress is on standard error: a header (model, `approval`, `sandbox`), then each command Codex runs, with its output.
2. **Exit codes.** 0 when a review was written. 1 on failure, with an `ERROR:` line on standard error and nothing on standard output.
3. **A missing base isn't a failure.** Given a base that doesn't exist, Codex picks another and reviews against that.
4. **Uncommitted changes are included.** Codex diffs the working tree against the merge base.
5. **Sandbox.** A review runs with `sandbox: read-only` and `approval: never` by default, but a host's `sandbox_mode` setting loosens it. `-c sandbox_mode="read-only"` pins it. The sandbox also stops the reviewer running a repository's checks.
6. **Model.** `-c review_model="<model>"` sets the model the review runs on. The header still names the session's model.
7. **Input.** It doesn't wait on open input. Input is closed anyway.
8. **Guidance.** It reads `AGENTS.md` and follows it to `REVIEW.md`.
9. **Effort.** `-c model_reasoning_effort="<level>"` sets how hard the reviewer thinks. With none set, the header reports `reasoning effort: none`. `high` and `xhigh` are both accepted on the default model.
