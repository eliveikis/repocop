# Coordinator v0.1 Requirement

## High-Level Requirement Goals

Build a first working version of a local development coordinator for managing Claude Code work across multiple unrelated Git repositories.

The coordinator should act as the primary control plane for starting and monitoring repository-specific work, while keeping durable project knowledge and requirements inside each repository.

The initial version should optimize for simplicity and local use in WSL2. It should be designed so the same coordinator can later run on a Linux VPS or other always-on host without major architectural changes.

### 1. Coordinator UI

Provide a simple browser-based UI served by a Python application.

The UI should allow the user to:

- See all repositories known to the coordinator.
- Add/onboard a new repository from a Git remote URL.
- Open a repository dashboard.
- Create and edit requirements using a large text editor.
- Start predefined Claude Code workflows against a requirement.
- See the status of active and completed agent work.
- Open an individual Claude session for a repository/task.
- Send additional instructions directly to that Claude session.
- Inspect relevant execution output such as Claude messages, commands, test output, Git status, and diffs.
- Sync an onboarded repository with the current coordinator template.

The UI is server-rendered HTML (Jinja templates, with HTMX for live updates). Small, page-specific plain JavaScript or vendored libraries (e.g. a diff viewer or Markdown editor) may be added where a page needs richer interaction. There is no SPA framework and no frontend build toolchain. Rationale: [specs/architecture.md](../../architecture.md) ADR-005.

### 2. Repository Ownership of Project Knowledge

Each repository remains the source of truth for its own durable project information.

The coordinator must not maintain duplicate authoritative copies of requirements, specifications, design documents, Claude configuration, or implementation history.

A typical onboarded repository may contain:

```text
repo/
├── CLAUDE.md
├── README.md
├── .claude/
│   ├── skills/
│   ├── rules/
│   └── settings.json
└── specs/                    # the single authority for design
    ├── index.md              # starts with the root design files, then lists everything else
    ├── product.md            # root: vision, pillars, audience, platforms, monetization, roadmap
    ├── architecture.md       # root: high-level architecture, Mermaid diagrams, decisions
    ├── <area>.md             # optional: added when a feature earns its own design doc
    └── changes/
        ├── todo/             # requirements (change requests) not yet delivered
        └── archive/          # delivered changes
```

Existing repository conventions should be preserved when possible.

The coordinator may maintain references and execution metadata that point to files in a repository.

### 3. Requirement Workflow

The coordinator should provide a convenient front door for requirement-driven development.

The user should be able to select a repository, create a requirement, and edit requirement text in the coordinator UI.

The requirement file itself must be stored inside the selected repository.

Each requirement has a **name**, a **body**, and a **kind** (`feature` or `fix`), all edited in the UI. The coordinator gives it a global id, and the file is named `req-<id>-<slug>.md` (e.g. `req-123-bulk-user-import.md`). The file contains `# <name>` followed by the body.

When a requirement is saved through the UI, the coordinator commits that file, and only that file, on the primary checkout's current branch, so agent worktrees always see it. If a requirement file is uncommitted when a task is started (for example after a manual edit), the coordinator blocks the task and tells the user, offering to make the same single-file commit.

The coordinator should support invoking existing Claude Code skills/workflows such as:

- `review-requirement`
- `implement`
- `address-pr-comments`

The exact contents and behavior of those skills belong to the repository and are not hard-coded into the coordinator beyond invoking them.

### 4. Repository Onboarding

The coordinator should make adding a new repository simple.

Given a Git remote URL, it should be able to:

1. Determine whether the repository is already registered/cloned, matching on the normalized remote URL and on the primary path.
2. Clone it if necessary.
3. Register its local path.
4. Apply standard coordinator-managed bootstrap files where missing.
5. Prepare the repository for Claude Code use.
6. Leave the repository ready for requirement-driven work.

The coordinator should own a canonical bootstrap/template directory containing defaults such as:

```text
templates/
└── default-repo/
    ├── CLAUDE.md
    ├── README additions or template guidance
    ├── .claude/
    │   ├── skills/
    │   ├── rules/
    │   └── settings.json
    └── specs/
        ├── index.md
        ├── product.md        # stub with section prompts
        ├── architecture.md   # stub with section prompts + example Mermaid block
        └── changes/
            ├── todo/
            └── archive/
```

Onboarding should copy or instantiate these into the repository rather than making the repository depend directly on the coordinator template at runtime.

Existing files must not be destructively overwritten without explicit user action.

#### Template Sync

The user should be able to bring an already-onboarded repository up to date with the current coordinator template at any time.

1. The coordinator compares every template file (after template substitution) with the repository's default branch and classifies it as **missing**, **identical**, or **differs**.
2. The UI shows this plan, including a diff for every file that differs.
3. The user chooses per file: create (missing files), overwrite, or keep (files that differ). Nothing is selected for overwrite by default.
4. The chosen changes are applied in a **coordinator-owned worktree on a new branch**, never in the human-owned primary checkout. The user reviews and merges that branch like any other agent branch.
5. The sync is recorded as a task (workflow `template-sync`), so its branch, worktree, git status, and diff are visible on the normal task page. No Claude session is needed.

Some template files are only a starting point, and some must keep the repository's own content. The template declares each such file's kind:

- A **starter** file (e.g. `CLAUDE.md` and the spec stubs) is created when missing and is the repository's own after that. Sync never offers to overwrite it.
- A **merged** file (e.g. `.claude/settings.json`) is JSON. Sync offers to add the template's entries it lacks, and never changes or removes what the repository has.
- Every other file syncs as above.

Template version tracking and automatic three-way merging are out of scope (see §13). When both the template and the repository changed a file that isn't merged, the user picks one version per file.

### 5. Worktree Isolation

The user's normal checkout must be treated as human-owned and must never be used by coordinator-controlled agents for implementation work.

Example:

```text
~/code/crm-api/                  # human-owned checkout
~/agent-worktrees/crm-api/...    # coordinator-owned worktrees
```

When the coordinator starts agent work on a requirement, it should automatically create a dedicated Git worktree and branch for that requirement, or reuse the ones it already created. All tasks for one requirement (review, implement, address PR comments) run in the same worktree, one at a time.

Example:

```text
~/agent-worktrees/crm-api/req-123-bulk-user-import/
```

This allows the user to safely run:

```bash
cd ~/code/crm-api
claude
```

without conflicting with coordinator-controlled Claude processes.

The coordinator should refuse to run an implementation agent inside the repository's primary human checkout.

### 6. Claude Session Isolation

Each active task should have its own Claude Code process/session associated with exactly one repository worktree.

Conceptually:

```text
Coordinator
├── repo-a
│   └── task/session A
├── repo-b
│   └── task/session B
└── repo-c
    └── task/session C
```

A Claude session should inherit the configuration of the repository/worktree it is running inside, including `CLAUDE.md`, `.claude/rules`, `.claude/skills`, and `.claude/settings.json`.

The coordinator should not create one Claude session with simultaneous write access to several unrelated repositories.

### 7. Direct Interaction With Running Claude Sessions

The UI should allow the user to inspect and interact with an individual repository/task session.

The user should be able to send a direct instruction such as:

```text
Do not use the existing parser. Use the streaming implementation instead.
```

That instruction must be delivered only to the selected Claude session.

The UI should expose useful visible execution information, including:

- User instructions.
- Claude's visible responses and progress summaries.
- Commands/tool activity when available.
- Test/lint/build output.
- Current Git status.
- Current diff.
- Branch/worktree information.

The system should not depend on exposing Claude's private chain-of-thought. User-visible summaries and observable actions are sufficient.

### 8. Thin Coordinator Architecture

The initial coordinator should be a small orchestration layer, not a complex multi-agent framework.

Its responsibilities are primarily:

- Repository registry.
- Requirement routing.
- Worktree lifecycle.
- Claude Code process/session lifecycle.
- Workflow invocation.
- Execution state.
- User interaction.
- Visibility into Git and command results.

Repository-specific reasoning, coding conventions, skills, and rules should remain inside each repository.

### 9. Claude Authentication

Claude sessions use the host's Claude Code subscription login (e.g. a Max plan) by default, so running workflows draws on the subscription rather than a separately billed API key. An API key can be configured instead as an explicit option. The main page shows which one sessions are using.

## Acceptance Criteria

### A. Application and UI

- [x] The coordinator runs locally in WSL2 with a single documented command.
- [x] Opening the application in a browser shows a repository list.
- [x] The application uses Python and FastAPI.
- [x] The first version uses server-rendered HTML.
- [x] Jinja templates are sufficient for the initial implementation.
- [x] HTMX may be used where it materially simplifies interactive updates.
- [x] No React/Vue/other SPA framework is required.
- [x] Any page-specific JavaScript is plain or vendored into `coordinator/static/`, with no build step and no CDN dependency at runtime.

### B. Repository Registry

- [x] Repositories can be registered with at least:
  - logical name
  - Git remote URL
  - primary checkout path
  - coordinator worktree root
- [x] Repository configuration survives coordinator restarts.
- [x] The coordinator can detect whether a configured repository exists locally.
- [x] The UI shows whether a repository is ready, missing, or requires setup.

### C. Repository Onboarding

- [x] The UI has an "Add repository" flow accepting a Git remote URL.
- [x] A repository that is not present locally can be cloned.
- [x] Re-adding an already known/cloned repository does not duplicate it.
- [x] A repository already cloned under the repositories root can be added by its folder name alone, with its remote URL read from its `origin`.
- [x] Bootstrap/template files can be applied.
- [x] Existing `CLAUDE.md`, `.claude`, `README.md`, spec, or design files are not silently overwritten.
- [x] Missing standard directories/files can be created.
- [x] The resulting repository can immediately be selected for requirement work.

### C2. Template Sync

- [x] An onboarded repository can be synced with the current template from its dashboard.
- [x] The sync plan classifies each template file as missing, identical, or differs, and shows a diff for each file that differs.
- [x] The user chooses per file, and no existing file is overwritten unless the user selected it.
- [x] Changes are applied on a new branch in a coordinator-owned worktree. The primary checkout is unchanged.
- [x] The sync appears as a `template-sync` task with its branch, worktree, git status, and diff.
- [x] Running a sync when everything is identical reports "up to date" and creates no branch.
- [x] A starter file the repository has is shown as its own and never offered for overwrite. A missing one is offered for creation.
- [x] A merged file is offered only an add-only merge, with a diff, and a file that isn't a JSON object is shown with the reason it can't be merged.

### D. Requirements

- [x] The user can create a requirement from the coordinator UI.
- [x] The user selects the target repository before creating it.
- [x] The user can enter a title and 200-2000+ characters of requirement text comfortably.
- [x] Each new requirement gets a global id and is saved as `req-<id>-<slug>.md`, containing `# <name>` followed by the body.
- [x] The user can mark a requirement as `feature` or `fix`.
- [x] Starting a task on a hand-made requirement file without a `req-<id>-` prefix is blocked with an option to assign an id, which renames the file in a commit containing only that rename.
- [x] The requirement is saved inside the selected repository.
- [x] The user can reopen and edit the requirement.
- [x] Saving a requirement in the UI commits only that file on the current branch; other staged or modified files are untouched.
- [x] Saving is refused, with a visible reason, while the primary checkout is mid-merge, mid-rebase, or on a detached HEAD.
- [x] Starting a task whose requirement file is uncommitted is blocked with a visible notification and an option to commit it.
- [x] The coordinator stores only metadata/reference information outside the repository.
- [x] Existing repository requirement/spec conventions can be configured instead of forcing one fixed path.

### E. Claude Workflow Invocation

- [x] A requirement page can invoke a repository skill/workflow.
- [x] At minimum, the implementation can invoke:
  - `review-requirement`
  - `implement`
  - `address-pr-comments`
- [x] The command runs with the correct repository/worktree as its working directory.
- [x] Output is associated with the correct task/session.
- [x] Failures are surfaced in the UI rather than silently ignored.
- [x] Claude sessions use the host's Claude Code subscription login by default, even when an API key is set in the coordinator's environment.
- [x] An API key can be configured instead, and sessions then use it.
- [x] The main page shows whether sessions use the subscription (with its plan) or an API key, or why neither works.
- [x] A session that reports a different credential than the configured one is stopped with a visible reason.

### F. Agent Worktree Isolation

- [x] The primary checkout is explicitly marked as human-owned.
- [x] Implementation work initiated by the coordinator creates a separate Git worktree.
- [x] Each worktree has its own branch.
- [x] Worktrees are created beneath a coordinator-controlled root outside the primary checkout.
- [x] The coordinator refuses to start implementation in the human-owned checkout.
- [x] Two unrelated tasks may run in separate worktrees without modifying each other's files.
- [ ] The user can continue using Claude manually from the primary checkout while a coordinator task is running.

### G. Session Interaction and Visibility

- [x] Each active task has a detail/session page.
- [x] The page shows repository, branch, worktree, status, and current workflow.
- [x] The page shows Claude/user-visible transcript or execution messages.
- [x] The page shows relevant command/process output.
- [x] The page can show current `git status`.
- [x] The page can show the current diff.
- [x] The user can send an additional instruction to the selected running Claude session.
- [x] Instructions sent to one session are not delivered to any other session.
- [x] Once no task is active in its worktree, a task's page shows the command to continue its Claude session in a terminal.
- [x] The design does not require access to hidden chain-of-thought.

### H. Task State

- [x] The coordinator persists enough state to recover its task list after restart.
- [x] Each task records at least:
  - ID
  - repository
  - requirement path if applicable
  - workflow/action
  - branch
  - worktree path
  - status
  - creation/update timestamps
- [x] Suggested statuses include:
  - `queued`
  - `running`
  - `waiting_for_user`
  - `completed`
  - `failed`
  - `cancelled`
- [x] Task state is coordinator-owned execution state, not duplicated project specification content.

### I. Safety and Operational Constraints

- [x] Shell/process invocation avoids unsafe string concatenation where practical.
- [x] Git remote URLs and filesystem paths are validated before use.
- [x] The coordinator does not overwrite existing project files silently.
- [x] The coordinator clearly distinguishes human-owned and coordinator-owned working directories.
- [x] The architecture does not assume the coordinator will always run on WSL2.
- [x] Paths/configuration are externalized sufficiently to allow later deployment on Ubuntu/Hetzner.

### J. First-Draft Definition of Done

A first draft is considered working when the following end-to-end flow succeeds:

```text
1. Start coordinator.
2. Open browser.
3. Add an existing or new Git repository.
4. Coordinator clones/registers and bootstraps it.
5. Create a requirement in the UI.
6. Requirement is stored inside the repository.
7. Run review-requirement against it.
8. Start implementation.
9. Coordinator creates a separate branch/worktree.
10. Claude runs in that isolated worktree.
11. View session output from the browser.
12. Send an additional instruction to that session.
13. View Git status/diff for the agent worktree.
14. Primary checkout remains untouched by coordinator implementation work.
```

Demonstrate it with an automated walkthrough that uses the fake Claude CLI, plus one manual run with real Claude.

## Implementation Notes

### 1. Suggested Technology

Use:

```text
Python 3.12+
FastAPI
Jinja2
Uvicorn
HTMX optionally
SQLite
Git CLI
Claude Code CLI
```

Avoid introducing a frontend build toolchain for the first version.

SQLite is preferred for coordinator state because it is local, simple, inspectable, and easy to migrate later.

### 2. Suggested Coordinator Repository Layout

A reasonable initial structure:

```text
coordinator/
├── README.md
├── pyproject.toml
├── coordinator/
│   ├── main.py
│   ├── config.py
│   ├── db.py
│   ├── models/
│   ├── services/
│   │   ├── repositories.py
│   │   ├── git.py
│   │   ├── worktrees.py
│   │   ├── requirements.py
│   │   └── claude.py
│   ├── routes/
│   ├── templates/
│   └── static/
├── templates/
│   └── default-repo/
├── data/
└── tests/
```

Do not create unnecessary abstraction layers merely to match this suggestion.

### 3. Coordinator Configuration

Use a small config file or environment variables for host-specific paths.

Example:

```yaml
repos_root: /home/ed/code
worktrees_root: /home/ed/agent-worktrees
database_path: /home/ed/.local/share/coordinator/coordinator.db
```

Do not hard-code usernames or machine-specific paths.

### 4. Repository Model

A repository record should contain something similar to:

```text
id
name
remote_url
primary_path
worktrees_root
default_branch
requirement_path_pattern
created_at
updated_at
```

The coordinator should query Git for facts such as current branch and remotes rather than duplicating them unnecessarily.

### 5. Requirement Storage

A new repository may default to:

```text
specs/changes/todo/req-<id>-<slug>.md
specs/changes/archive/
```

However, make the requirement path configurable per repository.

The coordinator should save Markdown directly.

A requirement created through the UI should remain a normal file that can be edited manually in the repository.

The coordinator should not require proprietary metadata inside the requirement file unless necessary.

### 6. Bootstrap Strategy

Keep the canonical default boilerplate in:

```text
templates/default-repo/
```

On onboarding:

- detect what already exists
- show what will be created and let the user confirm it
- create missing files/directories
- preserve existing files by default

Where a file needs repository-specific content, use minimal template substitution.

Do not make onboarded repositories depend on symlinks back into the coordinator repository.

Seed `.claude/skills/` from this repository's own skills, copying each skill folder whole with its helper scripts.

For template sync (§4 Template Sync), reuse the same plan logic, extended with an **identical/differs** comparison against the repository's default branch. Then:

- create the task first, so the worktree and branch follow the normal naming (see `specs/architecture.md`)
- write the selected files in that worktree and commit them with a message that lists each file and its action
- mark the task `completed`. Merging the branch is left to the human.

### 7. Git Worktree Strategy

For requirement `req-123` "Bulk user import" (kind `feature`) in repository `crm-api`:

```text
primary:
~/code/crm-api

agent worktree:
~/agent-worktrees/crm-api/req-123-bulk-user-import

branch:
feature/req-123-bulk-user-import
```

A `fix` requirement uses `fix/req-<id>-<slug>`. Tasks without a requirement (e.g. template sync) use `chore/<workflow>-<task-id>`. Every task for a requirement reuses its worktree and branch. Only one task may be active per requirement at a time.

Before creating a worktree, validate that:

- the primary repository is a valid Git repository
- the intended branch/worktree does not already conflict (an existing branch the coordinator didn't create is refused, not reused)
- the target path is beneath the configured worktree root
- the requirement file (if any) is committed

Create the worktree from the primary checkout's current HEAD and record that commit as the task's base commit, so the diff view can show everything the task changed.

The coordinator should record the worktree path and branch in task state.

Do not automatically delete completed worktrees in the first implementation unless cleanup is explicit and safe.

Git never prompts. Every git call runs with `GIT_TERMINAL_PROMPT=0` and stdin closed, with `-o BatchMode=yes` appended to the configured `core.sshCommand` (default `ssh`) via `GIT_SSH_COMMAND`, and network calls have a timeout. A missing credential or unknown host key then fails fast with a readable error instead of hanging.

### 8. Claude Code Integration

Wrap Claude Code invocation behind one service/module.

The rest of the application should not construct Claude CLI calls directly.

The wrapper should be responsible for:

- working directory
- process creation
- workflow/prompt input
- stdout/stderr capture
- session identifiers if available
- cancellation
- status updates

Prefer supported Claude Code CLI/session mechanisms rather than terminal emulation where possible.

Repository-specific skills should be invoked by name and allowed to resolve from that repository's `.claude` configuration.

### 9. Process Model

For the first version, running Claude processes as child processes of the FastAPI coordinator is acceptable.

The implementation should nevertheless separate process state from HTTP request lifetime.

A long-running Claude process must not block a FastAPI request handler.

Use a basic background process/task manager inside the application.

Do not introduce Celery, Redis, Kubernetes, or another distributed job system for the first version.

### 10. Session UI

A repository/task page should provide a practical operator view.

Suggested information:

```text
Repository: crm-api
Requirement: req-123 Bulk user import
Workflow: implement
Status: running
Branch: feature/req-123-bulk-user-import
Worktree: ~/agent-worktrees/crm-api/req-123-bulk-user-import

[ activity / transcript ]

[ direct instruction textarea ]

[ Send instruction ]

[ Git status ]
[ Diff ]
[ Cancel ]
```

Polling via HTMX is acceptable for the first version.

WebSockets are not required unless they are demonstrably simpler.

### 11. Human Intervention

The coordinator should make human intervention normal and inexpensive.

A running task may reach `waiting_for_user`.

The user can then send clarification or correction from the task page.

The implementation should preserve the association between the human message and the correct Claude session/task.

### 12. Manual Claude Usage

The coordinator must coexist with normal terminal-based Claude Code usage.

The primary checkout is intentionally left available for:

```bash
cd ~/code/<repo>
claude
```

The coordinator should not attempt to intercept or manage manually started Claude sessions.

Isolation is achieved by keeping coordinator implementation work in separate worktrees.

### 13. Scope Boundaries for v0.1

Do not implement these unless they are required to make the basic flow work:

- Multi-user authentication.
- Public internet deployment.
- Kubernetes.
- Distributed workers.
- Redis/Celery.
- Complex DAG workflow engines.
- Agent-to-agent messaging.
- Automatic multi-repository implementation by one agent.
- GitHub/GitLab webhooks.
- Automatic PR merging.
- Sophisticated permission systems.
- A React/Vue frontend.
- A generalized plugin framework.
- Full template migration/version management: template version tracking, automatic three-way merges, and bulk sync across many repositories. (Single-repository sync with per-file choices *is* in scope; see §4 Template Sync.)
- Remote VPS execution.

The goal is a useful local coordinator with clean boundaries that can evolve later.

### 14. Design Principle

Prefer:

```text
coordinator owns execution
repository owns knowledge
worktree owns isolated changes
Claude session owns one task context
human keeps final control
```

The first implementation should prove this model end-to-end before adding more autonomous orchestration.
