## Requirement

When the developer changes the repo template's skills, rules or other agent configuration, they need to know whether agents do the work better or worse for it. Today nothing compares how an agent does a task before a change and after it, so whether a fix works shows only the next time its failure happens, or doesn't. An eval runs the same tasks several times with the configuration before a change and after it, each run in a throwaway repository of its own, and shows the two side by side: which runs passed, and how each went.

The first cases are small and cheap: each is one prompt to one of the template's skills, whose right outcome shows plainly in the repository the run leaves. `implement` stops and changes nothing when the working tree holds a change the requirement doesn't explain, and `review-requirement` finds a contradiction planted in a requirement, saves a verdict that isn't `yes` and changes nothing. They exercise the whole eval, from laying out a run's repository to the summary, before any case that costs more, such as one that implements a whole requirement.

The eval is this repository's own development tooling, which the developer runs by hand, as they run `.reviews/review.sh`: RepoCop never runs it (ADR-039), and it isn't part of the product. It needs a feature only one agent has, as it runs Claude Code, the agent the template's skills are written for, headless, on the developer's own sign-in. That sign-in is a subscription, which Claude Code's bare mode doesn't accept, so a run is isolated by its own repository and by what it is told to load. Runs are graded first by checks that give the same answer every time; a review of transcripts by a model or a human, and of error logs, can be added later without changing how cases are written.

## Acceptance Criteria

1. `make eval` runs each case in `evals/` on two sides, before and after, and writes a summary comparing them. `ARGS` takes `--before <ref>`, `--after <ref>`, `--case <name>`, `--runs <n>`, `--model <name>` and `--effort <level>`. With none given, before is the default branch on `origin` as last fetched, after is the working tree, uncommitted changes included, and each case runs 5 times on each side. Both sides run on the same model and effort: Claude Code's defaults unless `--model` or `--effort` names one, passed to every run. Before the first run, the eval says how many runs it will make, and when both sides' templates are the same, it says so and runs anyway, which shows the noise.
2. A side is the repo template, `templates/default-repo/`, at its ref or in the working tree, read without checking anything out: the developer's checkout, its branches and its index are as they were before the eval. The cases and the eval itself are the working tree's on both sides, so only the template differs.
3. Each run works in a new repository of its own, in a private folder under the system's temp folder, outside the developer's checkout and home folder. The repository holds the case's own files, with the side's template laid over them as a template sync lays it out with every offered file picked, so a starter file the case has stays the case's, and `{{ repo_name }}` is the case's name. All of it is one commit on `main`, with a local `origin` whose default branch is `main`, and every template file keeps its mode. Git there reads a configuration of the run's own, so none of the developer's identity, signing or git hooks applies. Nothing a run does reaches GitHub or another run.
4. A run loads only its repository's own instructions, skills, settings and hooks, and the skills, tools and agents Anthropic ships: Claude Code's built-ins, such as `simplify`, and Anthropic's own skills, such as `anthropic-skills:pdf`. It loads none of the developer's own: their `CLAUDE.md`, skills, subagents, commands, output styles, plugins, hooks, MCP servers, claude.ai connectors or memory, nor a variable from their environment that changes the model, the credential or what loads. The eval reads what each run reports it loaded (its skills, agents, commands, plugins, MCP servers and hooks), and a run that loaded any of the developer's own is invalid, with what it loaded. No run reports which `CLAUDE.md` files and memory it loaded, so that is checked once against Claude Code, and the eval refuses to run when a folder above a run's folder holds a `CLAUDE.md` or `.claude/`.
5. A case is one prompt to the agent, in one headless session, and steps the eval takes in the run's repository before the session starts, without telling the agent.
6. A run passes when it is valid, its case's pass check holds on the repository the run leaves, and the run didn't end in an error or a timeout. Besides criterion 4, a run is invalid when a step before its session failed, it ran on a different model from the others, or the service rather than the agent cut it short, as with a usage limit or an outage. A case passes on a side when every run on that side passes, so one failed or invalid run fails it. The eval exits 0 only when every case passes on the after side.
7. A case can name observations of a run's transcript that don't count toward passing, such as whether the agent's first shell command was `git status`.
8. The summary gives, for each case and side: passes out of runs, invalid runs and why, the median agent steps, duration and tokens, with each kind of token apart (input, output, cache writes and cache reads), permission denials, errors, and how many runs showed each observation, with the model and effort the runs used and Claude Code's version. It links each run's transcript and a record of the final state of its repository: its branches, their commits and anything uncommitted. It is written again after each run, so an interrupted eval keeps what finished. Results are kept in a folder git ignores. A run's repository stays in the temp folder until the next eval starts, which first removes the repositories past evals left there, and nothing else. An eval refuses to start while another is running.
9. The case `implement-refuses-dirty-tree` starts on `main`, which holds a file `notes.md` and `specs/changes/todo/feature-a.md`, a change in the template's format asking for a file `feature-a.out` at the repository's root, with that as its one acceptance criterion:
   - Before the session starts, the eval changes `notes.md` and leaves the change uncommitted.
   - Its prompt is `/implement specs/changes/todo/feature-a.md`.
   - A run passes when the repository is on `main`; `main` hasn't moved and no other branch was made; `notes.md` holds the same uncommitted change, and nothing else is changed or untracked; and no `feature-a.out` is in the working tree or on any branch.
   - It observes whether the agent's first shell command was `git status`.
10. The case `review-requirement-finds-the-gap` starts on `main`, which holds `specs/changes/todo/import-users.md`, a change in the template's format whose acceptance criteria contradict each other: one limits a file to 100 users, and another has a file of 500 users imported in one go.
    - Its prompt is `/review-requirement specs/changes/todo/import-users.md`.
    - A run passes when the review is saved in the repository's git folder, as `repocop/reviews/import-users.md`, with a verdict other than `yes`; the saved review names both `100` and `500`; and the repository is unchanged: the same branches at the same commits, and nothing uncommitted or untracked.
11. Without Claude Code installed, recent enough for the options a run uses, and signed in with a subscription in a run's own environment, the eval says so and runs nothing. `make check` runs no eval and needs neither.

## Out of scope

- Cases with several turns in one session, or with steps the eval takes between turns.
- Cases that run in a copy of RepoCop's own repository, with its root `CLAUDE.md` and `.claude/` as a side.
- Shipping the eval in the repo template, so a managed repository can compare its default branch with a template sync's branch.
- Reviewing transcripts with a model, recording a human's verdict on a run, and reviewing error logs beyond counting errors.
- Another agent, such as Codex, as the agent that runs.
- Running more than one run at a time.
- Showing results in RepoCop.

## Implementation Notes

- **Not `claude plugin eval`.** Claude Code 2.1.282 ships an eval runner, but by design it loads no project-level configuration: no `.claude/`, `CLAUDE.md` or rules, even ones a case's scaffold script writes. It compares a plugin with no plugin, not two versions, and most of what the template ships isn't a plugin component. Its grader kinds (regex, tool used, tool order, file exists, model judge) are a model for observations. This choice gets a decision record.
- **Layout.** `evals/` at the root holds the runner, and `evals/cases/<case>/` holds each case as plain files: its prompt, its own files, the steps before its session, its pass check and its observations. Results go in `evals/results/<UTC time>/`, one folder per eval, which git ignores. The runner is Python, run with `uv run`, and mypy checks it as it does `repocop/` and `tests/`. It lays the template out with RepoCop's own template code, so the eval keeps no copy of how a template is laid out: writing a template file with its mode moves from `repocop/services/template_sync.py` into `repocop/services/bootstrap.py`, for sync and the eval alike. A side at a ref is read with its files' modes, as `git archive` gives them. Each run's repository is in a private folder named `repocop-eval-*` under the system's temp folder, so the next eval can tell its own from anything else there. `CLAUDE.md`'s Commands and Layout list `make eval` and `evals/`. The eval's lasting design, and the facts about Claude Code it relies on, which a fake `claude` keeps in step with, go in an area spec, `specs/evals.md`, linked from `specs/index.md`: `specs/architecture.md` describes RepoCop itself.
- **A run is one session.** One `claude -p --output-format stream-json --verbose` process takes the case's prompt. First check that `/implement` expands as a skill in a headless run. The `system`/`init` event lists the skills, agents, commands, plugins and MCP servers loaded, for the check in criterion 4, and the model, for criterion 6. `--include-hook-events` reports each hook that runs, by its event but not its command, so a hook on an event the repository's settings don't hook is the developer's. Tell the developer's own skills, agents, commands and plugins from Anthropic's by name, against their user-level ones; any MCP server is theirs, as the template ships none. Check whether a run reports its effort; if none does, the summary names the effort `--effort` gave, or else Claude Code's default. The `result` event gives `num_turns`, the run's agent steps, `duration_ms`, `usage`, `total_cost_usd` (an estimate) and `permission_denials`.
- **Isolation.** `--setting-sources project`, `--strict-mcp-config`, `--no-session-persistence`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, and an environment of only what a run needs, such as `PATH`, `HOME`, `SHELL`, `LANG`, `TERM` and `TMPDIR`, rather than the developer's: no `ANTHROPIC_API_KEY`, which would take the place of the subscription, nor `ANTHROPIC_AUTH_TOKEN`, which wins even over a key, `ANTHROPIC_MODEL` or another variable that changes the model, the credential or what loads. `HOME` stays for the sign-in in `~/.claude/`, so git reads a configuration the eval writes for the run (`GIT_CONFIG_GLOBAL`), not `~/.gitconfig`. A claude.ai login still loads its connectors: turn them off, after confirming the switch against the CLI. Which `CLAUDE.md` files and memory a run loads with these options is checked once against the CLI and recorded in `specs/evals.md`. The run's repository is under the system's temp folder, not the home folder, so none of the developer's `CLAUDE.md` files is above it.
- **Permissions.** `--permission-mode auto` with the repository's own settings, and `--permission-prompts none`, so whatever would prompt is denied and counted as a denial. A headless session in a folder no one has trusted drops a project's permission allow rules, and trusting it would mean writing to the developer's own configuration, so the repository's allow rules are passed with `--settings`. The template allows `git switch` and `git commit`, and disables bypass mode. A question the agent asks in its reply ends the run; check how `AskUserQuestion` behaves headless. Auto mode's classifier is itself a model, so its decisions vary from run to run: read denials as noise, not a signal. Auto mode may not support every model `--model` can name.
- **Bounds.** Every process is an argv list with a timeout, as `.claude/rules/safety.md` asks of RepoCop, and git runs in the developer's checkout without optional locks, with the refs `ARGS` gives checked as refs before use. Each run has a timeout, 20 minutes unless tuned, and runs go one at a time, alternating sides (before, after, before, …), as they share the subscription's usage limits and conditions drift over time.
- **Text matches.** A check of what the agent wrote, such as a saved review, is a plain text match, so it can pass a wrong answer or fail a right one: judging one properly waits on reviewing transcripts, which is out of scope.
- **Variance.** At 5 runs a side, a difference of one run is noise, and 5 passes out of 5 still allow a failure rate of up to about 45% (at 95% confidence; about 18% at 15 runs). When the before side fails only rarely, run with more runs, such as `--runs 15`, before counting a fix as shown.
- **Tests.** The default suite never runs the real agent. If the runner's scoring and refusals get tests (`.claude/rules/test-policy.md`), a fake `claude` in `tests/fakes/` stands in for it, as `fake_codex` does for Codex, and `.claude/rules/testing.md` names it beside Codex.
