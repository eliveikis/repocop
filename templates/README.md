# templates/

`default-repo/` holds the repo template: the files RepoCop brings into an onboarded repository through a template sync, a new repository's first files included. How sync applies it is in `specs/architecture.md` › Template sync.

Rules:
- Files here are **copied** into repos. Repos never depend on this directory at runtime and never symlink to it.
- **Template sync** compares these files with an onboarded repo's default branch on `origin` and applies only the files the user picked, on a worktree branch. Changing a file here therefore reaches repos only when someone syncs and merges, so keep changes deliberate and self-explanatory. A repo whose default branch is behind shows so on RepoCop's pages.
- **License.** The template is licensed MIT No Attribution, in `templates/LICENSE`, beside `default-repo/` rather than in it: a license file there would be copied into every onboarded repository, where the repository's own license belongs. MIT No Attribution asks nothing of the copies, so the files sync writes carry no obligation either.
- The only placeholder is `{{ repo_name }}`, replaced with the repository's name in text files.
- A `.gitkeep` only keeps an empty folder in this template. It isn't part of the template, so sync never offers it.
- **Not only for code** (ADR-020). An onboarded repo may produce software, writing or other media, so shipped files don't assume code. Code-specific guidance is marked as such ("In code: …"), and verification goes through the check command the repo's own `CLAUDE.md` documents, if it has one.
- **Copies of this repo's own files.** The files listed in `MIRRORED` in `tests/test_default_template.py` (the skills, the shared rules, the WSL hook and the guide to changes) are copies of this repo's. Keep them repo-agnostic and change both copies together. The test fails when they differ and prints the command that copies them over.
- **The guide to changes.** `specs/changes/README.md`, managed, says how a change goes from proposal to archive and how changes wait on each other, for people browsing the folder. Being managed, it reaches every repo on sync. `specs/index.md`, a starter file a repo then owns, only links to it; a repo created before the guide keeps its own Lifecycle section there until someone removes it.
- `.claude/settings.json` allowlists what the shipped skills run: read-only git, `git add`, `git commit` and `git mv` (skills commit their own work), `make check` and `make test`, and the skills' helper scripts, so they run without asking. `git push` is on "ask", so a push always asks first. Add an entry when a skill gains a command, and a repo whose check command isn't `make check` adds its own. `tests/test_default_template.py` checks the skills' commands are covered. The file also sets `attribution` to empty strings, so commits and pull requests made in the repo carry no Claude attribution. It turns off bypass-permissions mode (`disableBypassPermissionsMode`) and denies Claude's file tools reading `.env` files; a Bash command such as `cat .env` gets past that rule.
- **Linux tools only on WSL.** WSL appends the Windows `PATH`, so a Linux tool that is missing can resolve to a Windows one. The settings' SessionStart hook, `.claude/hooks/linux-only-path.sh` (plain `sh`), removes the Windows drives (`/mnt/<letter>/`) from the `PATH` of Claude's Bash commands and tells Claude to report a missing tool rather than use a Windows one. It does nothing off WSL. The `deny` rules block the Windows shells and anything run from `/mnt/`, including in interactive sessions where they would otherwise be approvable. Both act on the command text Claude writes, so they stop the usual forms but aren't a security boundary.
- **Sessions report themselves.** The settings register `.claude/hooks/session-events.sh` (plain `sh` and `awk`), `async`, on the session events RepoCop shows: a session starting, moving, starting a workflow, waiting for its user, going back to work, finishing its turn and closing. It appends one line per event to the repository's git folder, which every worktree shares and no commit holds, and picks out only the few fields RepoCop's format allows, never a prompt, a command or what the agent said. `specs/architecture.md` › Session events has the format and which Claude Code event gives which. It was verified on Claude Code 2.1.312, the oldest it supports, and `tests/test_session_hook.py` runs it on recorded payloads under `mawk` and `gawk --posix`. It does nothing that can fail a session, but sessions on a branch made before a sync brought it record nothing. The same script, registered again on `Stop` with `deliver` and waited for, hands a session the request RepoCop's page left for it in the git folder, once and only when it names a skill committed in the session's checkout and a requirement file there: `specs/architecture.md` › Session requests.
- **Pushed history stays.** `commits.md` allows amending only an unpushed commit, and an editor can push a branch without the session knowing. The settings' PreToolUse hook, `.claude/hooks/amend-only-unpushed.sh` (plain `sh`), checks each Bash command that mentions an amend: when `HEAD` is already on a remote-tracking branch, it refuses the command and tells Claude to make a new commit. An amend that points git at another directory (through `cd`, `-C`, a git dir or a work tree) is refused too, since the hook can't tell which checkout it amends. It matches the command's text, so a command that only mentions an amend is checked as well, and it knows only the pushes and fetches the checkout has seen. Permission rules can't do this: an auto-approved `git commit` slips past `ask`, and a hook runs whatever the permission mode.
- **File kinds** (ADR-021) are declared in `default-repo/template.toml`, which is never copied. A file it doesn't list is *managed*: it follows the template, and sync offers to overwrite it. A *starter* file is created when missing and is the repo's own after that, so sync never offers it; use this for anything a repo fills in. A *merged* file is JSON that sync brings up to date with the template: it adds what the template has and takes the template's values, and keeps what only the repo has (ADR-027). Put a value in a merged file only when every repo must have it, since a repo that changes it is offered it back on every sync. Mark a new file's kind when you add it, and see `specs/architecture.md` › Template sync for the rules.
- **Managed files carry a marker** (ADR-032) on their first line after any shebang or front matter: `<!-- managed by template -->` in Markdown, `# managed by template` in files whose comments start with `#`. Sync offers to delete a marked file the template no longer ships, so dropping or renaming a managed file here reaches repos too. Give every new managed file the marker, and never a starter or merged file: they hold the repo's own content, which sync must never delete. A file that can have neither comment, such as JSON, can't be managed. `tests/test_default_template.py` checks both.
- The shared `principles.md` rule, loaded in every session, points sessions at `specs/`, so `CLAUDE.md` doesn't need to.
- **Review guidance.** `REVIEW.md` is a starter stub a repo fills in with what a review of its changes checks and skips. `AGENTS.md` is a starter file that only points other coding agents, such as Codex, at `CLAUDE.md`, the rules and `REVIEW.md`. Both are the repo's own once created, so a repo that already has either keeps it. Keep `REVIEW.md` tool-neutral: more than one reviewer reads a file of that name.
- **Backlog graph.** `specs/changes/backlog.sh` checks each change's `depends-on` and draws `specs/changes/backlog.md`, using only `sh` and `awk`, so it runs in any repo as it is. The folder's own `.gitignore` keeps the drawing out of git, for the same reason as `.reviews/` below. RepoCop orders requirements by the same rules, and `tests/test_backlog.py` fails when the two disagree, under `mawk` and under `gawk --posix`.
- **Reviews by hand.** `.reviews/review.sh` runs Codex's review of the branch, read-only, and saves it in `.reviews/`, whose own `.gitignore` makes git ignore everything there but those two files. A repo's own `.gitignore` can't be given a line by sync, which is why the folder carries its own. The script owns its options, and `tests/test_review_script.py` checks its read-only sandbox and default effort.
- `CLAUDE.md`, `REVIEW.md`, `specs/product.md` and `specs/architecture.md` ship as short stubs: section headings with one-line prompts and `_TBD_` markers, plus one example Mermaid block in architecture.md. Don't require them to be filled in; `review-requirement` flags them when they're missing or empty.
