# Specs conventions

- **Root design files:** `specs/product.md` (why, for whom) and `specs/architecture.md` (how) state the current truth and stand alone. Edit them in place, with no history, decisions log or open questions. `architecture.md` says how the work is built: its goals, its main parts and what each may depend on, the contracts between them, its key flows, and where things live. It gives each part its role in a few lines and links to the area spec for how it behaves, rather than saying it. In code, its parts are components; in writing or media, they are such as sections, series and assets.
- **What a spec says.** A spec says what a part does and for whom, why, the rules it must keep, its key flows, and the contracts that something outside the work relies on, at the level of a user story. How the part does it, such as its limits, numbers, fields and steps, is the work's own: in code, each module, function and config key documents its responsibility, what it guarantees and how (`.claude/rules/principles.md`). What is too small to be design is stated only by the work and its checks. The level a fact belongs at decides where it goes, not where else it is already written.
- **Area specs** (`specs/<area>.md`) each describe one of a repository's few broad areas, never a single feature, and are linked from `specs/index.md`. An area spec is the one place its area's behaviour is stated, with the reasons that aren't plain from it. When a change's behaviour fits no area, the developer decides where it goes: an agent doesn't start an area spec on its own, or put behaviour in `architecture.md`.
- **Decision records** (`specs/decisions/adr-<nnn>-<slug>.md`, titled `# ADR-<nnn>: <the decision>`) say why an architecturally significant choice was made: one that many later changes must work within and that is costly to undo. In code, examples are a boundary between components or what one may depend on, a contract between them (a protocol, a stored format, a determinism rule), the platform, the engine or a core library, and how environments are built. In writing or media, they are such as the formats the work is published in, the toolchain that builds it, and the structure every part follows. How a feature behaves is not one, however hard it was to settle: its area spec says it, and a smaller choice's reason goes in the commit message. Write a record when its choice is made, numbered after the highest in `specs/decisions/` and its archive, as `git ls-files specs/decisions` lists them: status and date, context, decision, consequences, and alternatives rejected with why.
- **A record is history; the specs are the truth.** Where a record and a spec differ, the spec holds, and no change reconciles older records with it. Once accepted, a record is edited only to say what superseded it: a line at its top names the record that replaced a part of it. A record replaced whole, or whose choice isn't architecturally significant, moves to `specs/decisions/archive/` when a change supersedes it or the developer asks. Records name each other by id (`ADR-029`), never by a link, so a move breaks nothing. Read a record only before changing what it decided. Never load the records' archive, or cite an archived record anywhere but in another record.
- **Changes** live in `specs/changes/todo/` as `<slug>.md`, with no id. Once one is delivered, `/complete-change` folds its lasting design into the specs and moves it to `specs/changes/archive/`, its file name stamped with the UTC time it was archived, without colons, which Windows file names can't hold: `2026-10-14T150616Z-bulk-import.md`. An archived change stays readable as the record of what its branch delivered. Never edit one or link to one from specs, rules or skills: what lasts is in the specs.
- **Dependencies.** A change that needs others delivered first lists them in its front matter, one name per line under `depends-on:`, each as `  - <name>`. A change's name is its file name without `.md`, its archive stamp, and the `req-<id>-` prefix older changes carry. A name that matches a change in the archive counts as delivered and no longer holds anything up. Leave it in the list once it's delivered: it records what the change built on. `specs/changes/backlog.sh` checks every change's list and draws the backlog in `specs/changes/backlog.md`, which git ignores: a Mermaid graph, then the changes in the order they can start. `--check` only checks.
- **A branch's requirement.** A branch belongs to a requirement when its name is the requirement's name, alone or after its last `/`, as `bulk-import` and `agent/bulk-import` both are for `bulk-import.md`. Nothing else ties a branch to a change still in `todo/`: a change is often written and committed apart from the branch that delivers it, so a branch whose name matches no requirement belongs to none, whatever its commits add or edit there. A branch also delivers each change archived on it that the default branch hasn't archived, whatever its name: a change is archived only once its work is done, on the branch that did it, so merging a branch lands the work of each change it archived, and a branch that merges several delivered branches delivers each of their changes.
- **A change's format.** No title heading: its file name, and the branch it's delivered on, name it. Its sections, in this order:
  - `## Requirement` (required): the product story, in one paragraph of one to a few sentences, as an epic or a user story is, without the ritual "As a … I want … so that …". What will change and what value the change provides and for what reason. The beneficiary can be an end user, a developer or agent, a product manager, or code calling an API. Additional paragraphs may be added to provide more context when the intro requires definitions, a reason why the current features are insufficient, high level direction that provides context to the individual acceptance criteria, or to guide implementation if certain approaches should be adhered to.
  - `## Acceptance Criteria` (required): a numbered list of outcomes the beneficiary can observe, one per item, so each can be cited by its number. The beneficiary may be a tool or code calling an API. Not the steps of the work, which tests to write (`.claude/rules/test-policy.md` decides that), or what every delivery does anyway, such as passing the checks: technical direction the work must follow goes in Implementation Notes.
  - `## Out of scope` (optional).
  - `## Implementation Notes` (optional): only when the existing specs, rules and code don't settle the approach.
  - `## Open questions` (optional): each with a proposed default marked **→**.
- **Size** a change to be delivered in one go, on one branch and one PR. Split anything bigger into separate changes rather than staging work inside one.
- **A change is fixed once reviewed.** It states the work, not its progress: plain, checkable acceptance criteria, and open questions settled before implementation. After that only a human edits it, as the work is judged against it, and only when the work changes; an agent that finds it wrong or incomplete says what should change. Progress shows in the branch and its PR, never in the change, `CLAUDE.md` or the README, which later sessions take as current, and `product.md`'s roadmap stays at the level of themes.
- **Diagrams** are fenced ```` ```mermaid ```` blocks (flowchart, sequenceDiagram, stateDiagram-v2, erDiagram), not images or ASCII art. Keep labels short, quote any with punctuation, and avoid `<...>`, which Mermaid reads as HTML.
- **`specs/index.md` maps the design:** the root design files first, then the area specs, updated when one is added, renamed or removed. It says what decision records and changes are for but never lists them: each folder is its own list.
- Mark unknowns `_TBD: <question>_`. Don't invent product facts, or limits that close off a future design: a spec says what is true now, and Out of scope means not in this change, not never. A design that no change in `todo/` delivers is only an example of how a goal could be met, worded as one, and kept only where it gives context.
